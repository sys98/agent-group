# Codex App 工作树任务编排

**先检查当前编排是否已有 worker。** 已派发的 CLI 任务沿用其账本、工作树、会话和冻结合同，按 [既有 CLI 运行说明](references/legacy-cli-runtime.md) 收尾，合同恢复参考 [冻结任务合同](references/legacy-cli-task-contract.md)；不因技能升级迁移执行器、补建 App 聊天、重启或清理。账本没有 transport 字段时核对实际记录，不默认改为 App 模式。不要接管其他聊天的运行任务。

新编排参照 orca-dispatch 保留 coordinator → 独立 worker/worktree → 验收 → 集成的交付链。每个用户要求的新独立任务必须是 **Codex App 中可见、可进入、可继续的聊天，绑定独立分支和托管工作树**。只有创建了目录或 CLI 会话不算 App 任务。主代理负责调查、拆分、监督、复核与集成，不代写已派发的业务任务。

原生子代理可用于只读调查及 Matt `code-review` 的两个独立审查轴。工作树隔离来自本编排合同，不是 Matt 技能本身的要求。阶段对应与宿主差异见 [orca-dispatch-mapping.md](references/orca-dispatch-mapping.md)。

## 入口与边界

- 调用本技能选择编排方式，不重复问执行方式；但技能本身不授予新建 App 任务、给其他聊天发消息或归档的权限。执行前核对人类用户对这些独立任务的明确授权，记录创建范围、协调消息与生命周期范围；已有授权不重问。宿主若禁止为本请求的普通子步骤新建聊天，必须服从，不以本技能绕过。
- `先聊清楚`：按需求决策树澄清，必要时做一次性原型，形成规格后等待确认。
- `先确认`：完整计划与测试切入点提出后，等待明确答复再派发。
- `worker 用 <model>`：仅在用户明确指定且 App 工具支持时传模型；否则省略覆盖，使用新任务的配置默认值，不声称继承 coordinator 模型。
- `继续 <账本路径>`：核对记录的 App threadId、托管工作树与 Git 后续作同一聊天；归档恢复见 [生命周期](references/worktree-lifecycle.md)。
- 先读 [Matt 技能联动](references/matt-skill-routing.md)。按阶段**实际读取**原技能及其要求的参考，不能用本表代替。技能解析使用宿主技能目录与真实文件路径，不依赖作者机器路径。

## 0–1. 固定基线与项目规则

1. 读取项目根与涉及目录的 `AGENTS.md`、`CLAUDE.md`、`MEMORY.md`（大小写等价），已有规格、领域词汇与相关 ADR，提取实际测试、类型检查、lint、构建和提交约定。
2. 核对仓库、工作目录、分支、HEAD、远程和 dirty 状态。允许访问远程时 fetch，区分相同、落后、领先与分叉。干净默认分支允许按项目约定 ff-only；本地领先保留本地基线并说明；分叉先确定权威基线。不覆盖用户改动。
3. 记录显式完整基线 SHA 与集成目标分支。未提交输入不会自动进入新 worktree；先判定是否为本任务所需，必要输入未明确纳入基线前不派发，其他用户改动原位保留。
4. 读取 [App 任务运行说明](references/worker-runtime.md)，检查真实任务工具、匹配的已保存 Git 项目、授权与起点参数。缺少能力时报告具体阻碍；继续独立调查，不降级为 CLI worker 或共享目录实施，不借用另一个项目。

## 2. 调查：先解决事实和决策

- **bug**：加载 `diagnosing-bugs`，coordinator 完成阶段 1–4：实际运行能捕获用户症状的紧反馈命令，复现并最小化，公开 3–5 个可证伪假设，逐一验证。阶段 5–6 交 worker。没有有效反馈循环时说明尝试与缺失条件，不猜补丁。
- **功能**：读已有 PRD 与真实调用路径，再加载 `grilling`。只问未定且影响实现的决策；已写清的 PRD 不重问、不另跑 `to-spec`。有明确范围时最多两轮，未定默认必须披露且不能替代明确批准；`先聊清楚` 时持续到关键决策明确。用户说“够了”立即停止提问。
- 界面或状态逻辑无法靠文字确认时加载 `prototype` 的 UI/LOGIC 分支；保留完整原型的独立来源，正式规格记录结论，不把整个原型当生产代码。
- 仅一处琐碎改动可按 `orca-dispatch` 例外直接完成并说明。已建立的多 worker 流程不能借此例外改为 coordinator 代写。

## 3–4. 计划、测试切入点和任务合同

派发前向用户报告：根因或已定决策、证据、假设、范围与非目标、实现方案、风险，以及任务表。使用项目已有规格与计划位置；缺少规格时将本次计划保存为可供审查引用的文件，不额外创建同义规格。

coordinator 此时实际读取 `tdd`：每个公开测试切入点列明能抓到和抓不到的行为。取得用户明确确认，或引用本任务已有的具体确认；**不能把沉默或“计划已写”当成确认**。worker 只接收已确认的切入点，变更时回报 coordinator。必要答复未到，仅暂停依赖它的任务。

实际读取 `to-tickets`，按完整窄切片、真实 blockers、必要预重构优先和宽变更 expand–contract 拆任务；不能机械按前端/后端分票。任务计划集中展示粒度、依赖与验收，不另启动重复确认或擅自发布 tracker。这是沿用 `orca-dispatch` 的显式覆盖，详见 Matt 联动参考。

每项记录：逻辑 Task ID、波次/blockers、目标/非目标、归属、完整 base、projectId/hostId、真实 threadId 与原样标题、pending clientThreadId、工作树/分支、模型选择、验证与 seam 确认、证据、wait cursor、候选/集成 SHA，以及聊天/工作树各自的生命周期状态。同波冲突文件串行；公共合同与迁移顺序由 coordinator 统一确定。

每个 worker 使用 [任务合同](references/task-contract.md)，明确已选择直接实施、只在自己的工作树写入、不再派发实施子代理、不 push/merge/deploy、不改项目 MEMORY；需要决策时按实际运行协议报告 blocked 与问题。

## 5. 创建可见 App 任务，再开始实施

1. 按人类已授权的任务表，调用 `create_thread`，目标使用匹配的已保存 Git 项目和 `environment.type=worktree`；只在用户明确指定起点时填写对应 startingState，不编造分支或创建替代项目。
2. 创建 prompt 只执行初始化核对并停下，尚不改业务代码。记录回执；仅有 clientThreadId 时保持创建中，不能把它传给 read/wait/send，也不能重建一份任务。
3. 真实 threadId 出现后，用 App 列表/读取核实可见聊天、项目与 cwd，检查独立目录、common dir、完整 HEAD 和状态。初始化 turn 已结束后，在已授权范围建立任务分支，再核对；不让两个 writer 并行控制该分支。
4. 验收“App 可见 + threadId 可读取 + worktree/base 正确”后，才向该聊天发送已确认实施合同。当前波可启动任务先全部派发，再用 `wait_threads` 有界等待；记录 cursor，遵守能力上限。数据库、端口和产物另行隔离。
5. 结果未知或初始化失败时按 [生命周期](references/worktree-lifecycle.md) 核对原回执与实际资源，不盲目重试、删除或再起同文件 writer。向用户提供真实 App 任务入口，不能只给 CLI session ID。

## 6. 监督、提问和修复

- 用 `wait_threads` 的目标 ID、host 和 cursor 监督，详情按需 `read_thread`；完成/需关注才结算，超时不等于失败，不能只收到创建回执就退出。
- worker 缺决策时在自己的聊天报告 blocked、停止写入并结束 turn。coordinator 用已有事实答复，用户决策转给用户；在已有消息授权内用 `send_message_to_thread` 发回**同一 threadId**，保留聊天/工作树。worker 不因收到 coordinator 请求就获得向其他聊天发消息的权限。
- 修复继续同一任务/工作树/分支；默认发送 follow-up，不 fork 新聊天或创建替代 writer。若用户进入任务手工接管，coordinator 暂停该项自动派发，按最新人类指令重新核对边界。
- worker 只能执行合同内的项目检查与本地候选提交。权限不足或无正确测试切入点时回报；不扩大权限、改业务验收、伪造绿色结果或改用 coordinator 代写绕过。

## 7. 验收与 Matt 双轴审查

1. 确认任务 turn 和派生写入命令均已停止；核对实际工作树、任务归属、候选提交、基线祖先关系及 diff。dirty 或未跟踪的交付内容未固定前不能用 `HEAD` 冒充候选，聊天完成不等于业务验收。
2. coordinator 在该 worktree 亲自重跑适用检查，查看真实 diff、边界、安全与范围。工程检查与真实下载、部署、跨节点恢复等业务验收分开记录。
3. **实际加载 Matt `code-review`**，固定本波基线和候选 SHA，确认非空 diff。将同一比较命令与提交列表交给两个独立只读审查上下文：Standards 获得规范及原技能的**完整 smell baseline**，Spec 获得本次规格、合同与最新用户纠正。按原技能并行执行并分别呈现报告和计数，不能一轴掩盖另一轴。
4. 缺规格、缺独立审查能力或任一轴未完成，不能报双轴通过。原生子代理只能承担这里的只读审查或调查。发现问题交原 worker 修复，更新候选后重跑受影响检查与两轴审查，旧 SHA 的 verdict 不沿用到新候选。

## 8–9. 串行集成、清理与恢复

- 当前波全部验收后，在授权的集成分支按项目约定串行合并候选；无约定时沿用 `orca-dispatch` 的 `git merge --no-ff`。复核真实集成内容并跑 canonical 检查，通过后才以新基线启动依赖波次。
- 没有本地提交或集成授权时保留候选并报告待批动作。冲突或集成失败时保留现场与已通过结果，暂停依赖任务，不强行回退或偷偷跳过失败项。
- 按 [工作树生命周期](references/worktree-lifecycle.md) 执行：持久化证据 → 确认集成与 writer 停止 → 授权归档聊天 → 核实工作树/快照结果 → 最后安全删除已集成任务分支。聊天归档与物理回收分别记账；不得 raw Git 删除其他聊天的托管工作树。dirty、未集成、固定/共享/长期或归属不明的资源保留并报告。
- coordinator 将长期项目发现统一写入项目 MEMORY，并更新规格中的已确认决策；不写凭据。最终报告实际验收、候选与集成 SHA、各轴结果、未验证项、推送/部署状态、剩余工作与 MEMORY 是否更新。
- 中断后读持久账本与合同，核对原 threadId、App 状态、托管工作树与集成分支，再处理未决问题。已归档则按已授权恢复同一任务，不补建一批聊天；恢复路径、HEAD 或分支变化后旧验收不直接沿用。账本不是持久调度器，不承诺 coordinator 关闭后自动监督。
